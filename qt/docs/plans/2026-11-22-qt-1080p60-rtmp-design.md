# Qt 1080p60 RTMP 显示设计

日期：2026-11-22
状态：待用户复核
范围：`/home/chx/Linux/qiansai/qt`

## 1. 目标

在 WSL Ubuntu 22.04 中运行现有 Qt 上位机，通过
`rtmp://192.168.1.101:1935/live/test` 拉取 RK3588 推送的 H.264 流，
稳定显示完整彩色的 1920×1080@60fps 视频。

“跑通 1080p60”同时包含以下条件：

- 输入流由 `ffprobe` 确认为 1920×1080、约 60fps；
- Qt 解码速率和界面呈现速率在连续 10 分钟窗口内均不低于 59fps；
- 视频无黑带、错色、撕裂和比例变形；
- UI 操作保持响应，帧队列和进程内存不随时间持续增长；
- RTMP 暂时断开后能够自动重连，恢复后无需重启 Qt 程序。

## 2. 当前实现与问题

当前链路为：

```text
av_read_frame
  -> FFmpeg 软件解码
  -> sws_scale 转完整 1080p RGB32
  -> emit QImage（每帧一个 queued signal）
  -> QPixmap::fromImage
  -> Qt::SmoothTransformation 再缩放到 QLabel
```

已确认的风险：

1. 60fps 时每秒向 GUI 事件队列投递 60 张完整 RGB32 图像，GUI 一旦短暂落后就会积压旧帧。
2. 每帧先生成 1920×1080 RGB32，再在 GUI 线程平滑缩放，产生重复的像素搬运和缩放开销。
3. 无时间戳时使用 `decodedFrameCount * 33`，实际回退到约 30fps 时基。
4. 解码路径存在逐帧日志，会干扰 16.67ms 的帧预算。
5. 当前默认 RTMP 地址仍是旧地址 `10.36.113.231`。
6. 界面没有区分输入、解码和实际呈现 FPS，无法证明“显示 60fps”。

## 3. 方案决策

采用“FFmpeg 解码线程 + 单槽最新帧 + GUI 60Hz 消费”的稳定真 60fps 方案。

不采用以下方案：

- 保留逐帧 queued signal：修改少，但无法对 GUI 队列积压给出结构性保证；
- 本轮改为 GStreamer/硬解：WSL 图形与硬解后端存在额外不确定性，改造范围超过当前验收目标。

## 4. 数据流与线程模型

```text
RK3588 H.264 1080p60
  -> WSL nginx-rtmp（只转发，不转码）
  -> XVideoThread
       读取/解码
       按当前显示目标尺寸执行一次 sws_scale
       将结果覆盖写入 latestFrame（容量恒为 1）
       更新 decoded/input/dropped 计数
  -> PageCamera GUI 定时器（目标 60Hz）
       原子取得 latestFrame 快照
       仅在帧序号变化时更新 QLabel
       更新 rendered FPS 和延迟状态
```

关键不变量：

- 解码线程绝不等待 GUI 消费；
- `latestFrame` 只保存最新一帧，旧帧允许被覆盖；
- GUI 不接收逐帧 queued signal，事件队列长度不随视频时长增长；
- GUI 线程只负责生成/设置最终显示用的 pixmap，不再执行第二次平滑缩放；
- 帧槽读写通过短临界区保护，锁内只交换隐式共享的 `QImage` 和元数据。

## 5. 组件改动

### 5.1 `XVideoThread`

- 默认按低延迟 RTMP/TCP 参数打开流；
- 从 `avg_frame_rate`、`r_frame_rate` 和时间基推导有效帧率，禁止固定 33ms 回退；
- 提供线程安全的 `takeLatestFrame()`，返回图像、序号、PTS 和生成时间；
- 提供 `setOutputSize()`，窗口尺寸变化时更新转换目标；
- 仅在目标尺寸或输入像素格式变化时重建 `SwsContext`；
- 使用适合实时预览的快速缩放算法，避免 `SmoothTransformation` 二次处理；
- 删除逐帧日志，保留启动、重连、格式变化和周期性汇总日志；
- 维护输入包、解码帧、覆盖丢帧、错误和重连次数等计数。

### 5.2 `PageCamera`

- 默认地址改为 `rtmp://192.168.1.101:1935/live/test`，仍允许用户覆盖并持久化；
- 新增约 16ms 的 `Qt::PreciseTimer`，从最新帧槽取帧；
- 仅当帧序号变化时更新画面；
- 窗口/视频区域变化时计算保持宽高比的目标尺寸，并通知解码线程；
- 增加状态文字：输入尺寸、流标称 FPS、解码 FPS、显示 FPS、覆盖丢帧、连接/重连状态；
- 页面退出、停止播放和析构时停止定时器并安全结束解码线程。

### 5.3 构建配置

- 优先复用 WSL 已部署的 Qt 6.5.3 与 FFmpeg；
- 修正 `.pro` 中不可移植的 FFmpeg 路径时，使用可验证的 WSL 实际路径或 `pkg-config`，不复制新的 FFmpeg 私有构建；
- 不修改 RK3588 端编码链路和 nginx 转发配置，除非验收证明其未推送到约定地址。

## 6. 状态与错误处理

状态机：

```text
Idle -> Connecting -> Playing
                    -> Reconnecting -> Playing
                    -> Failed
Playing -> Reconnecting（读超时/EOF/网络错误）
Playing -> Idle（用户停止或页面销毁）
```

- 实时流失败后采用有上限的退避重连，停止操作可立即中断等待；
- 每次重连清理 FFmpeg 上下文和帧槽，禁止显示上一次连接的旧帧；
- 错误状态在界面显示简洁原因，详细 FFmpeg 错误保留在日志；
- 不因单帧解码错误退出整个线程，连续错误超过阈值才重连。

## 7. 测试策略

### 7.1 单元/组件测试

- 帧槽覆盖：连续写入多帧后只能取到最新序号；
- 并发访问：生产/消费循环下无死锁、竞态和队列增长；
- 帧率推导：60/1、60000/1001、无效分数和缺失 PTS 的回退正确；
- 尺寸计算：16:9 视频在不同控件尺寸下不变形；
- 停止/重连：停止请求能从阻塞读取和退避等待中退出。

### 7.2 WSL 确定性验证

先用本地 1920×1080@60fps H.264/TS 样本验证解码和 GUI 呈现，排除网络变量：

- 连续 10 分钟；
- 解码与显示均 ≥59fps；
- RSS 无持续线性增长；
- UI 可正常切页、缩放和停止。

### 7.3 RTMP 端到端验证

1. 启动 WSL `nginx-rtmp`；
2. 确认 `:1935` 监听以及 `/live/test` 有 publisher；
3. 用 `ffprobe` 记录实时流分辨率、编码和帧率；
4. 启动 Qt，记录 10 分钟输入/解码/显示/丢帧统计；
5. 截取 Qt 界面完整彩色画面作为视觉证据；
6. 临时中断 publisher，再恢复，验证自动重连；
7. 保存构建命令、运行命令、日志、截图和校验结果。

## 8. 完成判据

只有下列项目全部满足才声明完成：

- Qt 程序在 WSL 可重复构建、启动；
- 默认连接约定的 RTMP 地址；
- `ffprobe` 与 Qt 指标共同证明输入为 1920×1080、约 60fps；
- 连续 10 分钟解码 FPS、呈现 FPS 均 ≥59；
- 完整彩色画面通过截图人工检查；
- 无事件队列堆积、无持续内存增长、无崩溃；
- RTMP 断开恢复测试通过；
- 原始日志和操作步骤归档，未通过项不得包装为完成。

## 9. 非目标

- 本轮不重构板端 ISP、编码器或检测算法；
- 不承诺在 WSL 中启用 GPU 硬解；
- 不以“源流 60fps、界面显示 30fps”代替真 60fps 验收；
- 不把本地文件回放成功当作 RTMP 端到端成功。
